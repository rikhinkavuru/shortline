# Call design

The whole "script" is one task text and one result schema. CALL-E runs the conversation; Shortline decides what may be asked and what counts as an answer.

## Task text

Generated by `buildTaskText` in `src/domain/task.ts`. For amoxicillin 400 mg/5 mL oral suspension without a hold request:

> You are calling a pharmacy. Identify yourself immediately as an automated assistant calling for Shortline, a project that tracks medication availability, and say the call will take under a minute. If you reach a phone menu, choose the option for the pharmacy or to speak with pharmacy staff. Use the keypad when the menu asks for it. If you reach voicemail, do not leave a message and end the call. Once you are speaking with pharmacy staff, ask one question: whether they currently have amoxicillin 400 mg/5 mL oral suspension in stock and able to dispense today. If they say yes, ask whether supply is limited. If they say no or limited, ask when they expect the next delivery. Do not ask them to hold or reserve anything. Do not place an order, do not discuss any patient, do not ask about prices, and do not ask for anything beyond these questions. If they say they cannot share stock information over the phone, thank them and end the call. If they ask not to be called again, apologise, confirm you will note it, and end the call. Be brief and polite. Thank them and end the call as soon as you have an answer.

Design choices:

- **Disclosure first.** The callee learns who is calling before any question.
- **Phone menus.** CALL-E supports keypad IVR interaction (August 2026 release). Chain pharmacies almost always route through a store menu, so the text says what to press for.
- **One question.** Extraction quality falls with every extra ask; two follow-ups is the limit.
- **Refusals end the call.** A refusal is a data point about the site's policy, recorded as `refused_to_say`, and it rests the site for 90 days.
- **Hold, only when asked for.** `askHold` adds one sentence and one schema field. The text explicitly avoids giving a patient name.

## Recipient result schema

`buildRecipientResultSchema` produces a strict object (`additionalProperties: false`) using only features the Calls API documents as supported: `type`, `properties`, `required`, `enum`, `description`.

| Field | Values | Why |
| --- | --- | --- |
| `availability` | `in_stock`, `limited`, `out_of_stock`, `not_carried`, `refused_to_say`, `unknown` | The measurement. `unknown` is always allowed so the extractor is never forced to guess. `not_carried` corrects the frame. |
| `restock_expectation` | free text | Kept in the callee's words; shown, never parsed into a date. |
| `quantity_note` | free text | "a couple of bottles left" is more honest than an integer. |
| `answered_by` | `human`, `ivr`, `voicemail`, `unknown` | CALL-E does not return an answered-by disposition; the docs recommend extracting it. |
| `reached_pharmacy` | `yes`, `no`, `unknown` | Front-store clerks and wrong numbers must not become stock observations. |
| `do_not_call_request` | `yes`, `no` | Permanent opt-out trigger. |
| `evidence_quote` | free text | The shortest exact phrase supporting `availability`. Checked against the transcript. |
| `hold_response` (optional) | `offered`, `declined`, `not_asked`, `unknown` | Only with `askHold`. |

Field names avoid the reserved recipient response names (`summary`, `status`, `transcript`, `call_id`, timing fields) listed in the CALL-E docs.

A task-level `result_schema` with a single `pharmacies_reached` integer is also sent. The reconciler compares it with the count of recipients whose `reached_pharmacy` is `yes` and flags disagreement without changing any recipient result.

## Classification

`classifyRecipient` maps one recipient snapshot to an observation with an explicit `usable` verdict and reason.

```
recipient failed / canceled      → unreachable        (not usable)
structured_result null           → unknown            (no_structured_result)
answered_by voicemail            → voicemail
answered_by ivr                  → ivr_dead_end
reached_pharmacy no              → not_reached
availability refused_to_say      → refused
availability unknown             → unknown            (no_clear_answer)
answered_by/reached not confirmed→ <availability>     (pharmacy_staff_not_confirmed)
availability not_carried         → not_carried        (not_in_frame; site leaves the frame)
bot never named the product      → <availability>     (product_never_asked)
empty evidence_quote             → <availability>     (no_evidence)
quote not attributable to callee → <availability>     (evidence_unattributed, strict policy)
otherwise                        → <availability>     usable = true, "verified"
```

Attribution is lexical: at least 60% of the quote's content words must appear in the callee's turns. It is deliberately simple and deliberately strict. The dry-run scenarios include a schema-valid result whose quote is invented and a call where the assistant never named the product; both are shown in the dashboard as *not counted* with their reason, on every demo run.

When no transcript is available the observation is usable but flagged `quoted_without_transcript`; the dashboard shows the flag.

## Batch shape

One dispatch = one call task with up to `SHORTLINE_BATCH_SIZE` recipients (default 6). Metadata on every task: `dispatch_id`, `kind`, `watch_id`, `find_request_id`, `product_label`, `schema_version`, `app: shortline`. The reconciler refuses any call whose `metadata.dispatch_id` does not match the dispatch it is reconciling.

Per-recipient `region` is derived from the site's region code prefix (`US-CA-SF` → `US`) and `locale` is set for English-speaking regions; both are optional in the API and omitted otherwise.

## Things CALL-E could add that would make this better

Written down for the feedback survey:

1. A per-recipient confidence or an `answered_by` disposition in the Calls API, so gating does not depend on a transcript heuristic.
2. Signed webhooks. Today the receiver must treat every delivery as a wake-up and re-read through the API.
3. A distinct no-answer / declined code in the Calls API `failure_code` (the Goal Runs API has one; the Calls API does not guarantee it).
4. Per-recipient variables on batch call tasks, so a sweep across products could share one task.
5. A way to read a call task by idempotency key, so recovery after an ambiguous create does not require a replayed POST.
